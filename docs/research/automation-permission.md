# Automation permission off the terminal

Research for issue #3. Checked on 2026-11-10 against macOS 26.6.2 (25G83). Every claim is tagged **[V]** verified (Apple documentation, SDK headers, man pages, Apple DTS forum answers, or a read-only check on the development Mac), **[R]** reported by a third party (issue trackers, blogs, other tools' source) and not reproduced here, or **[I]** inferred. Nothing in this document was tested by triggering a prompt, resetting TCC or sending mail.

## Short answer

macOS does not grant Automation to `amail` or to `osascript`. It grants it to the "responsible" process, which is normally the GUI app at the top of the process tree: the terminal app, the desktop agent host, the IDE. Each host needs its own grant, and a host that is not allowed to prompt (hardened runtime without the Apple Events entitlement) fails instantly with -1743 and never shows a dialog. When a prompt is shown and nobody answers, the Apple event blocks; third parties report hangs of 2 to 15 minutes or more, so amail's own two minute deadline fires first and reports a timeout that hides the real cause. Error text is localised (41 localisations, and British English already spells it "Not authorised"), so only the trailing number is safe to match; amail already matches on the number. A binary can become its own permission holder by re-executing itself with responsibility disclaimed (a private libSystem call), but for an ad hoc signed Go binary the grant is tied to the exact build and path, so it is lost on every upgrade unless releases are signed with a Developer ID.

## Launch context versus who is prompted

"Responsible" below means the process TCC charges the request to. Apple DTS describes it as "the nearest 'parent' of the process that the user knows about" and adds that the algorithm "is complex and evolves over time" with no general API to control it ([forum 751802](https://developer.apple.com/forums/thread/751802), [forum 731504](https://developer.apple.com/forums/thread/731504)) **[V]**.

| Launch context | Responsible client | Who sees a prompt | Failure when nobody can answer |
| --- | --- | --- | --- |
| Terminal app, interactive | The terminal app. **[V]** On the development Mac a process four levels below the terminal (shell, agent CLI, shell, interpreter) reported the terminal app as its responsible process, and a silent permission query returned "granted" because the terminal already holds the grant. | The logged-in user, once per terminal app and target: "<Terminal> wants access to control Mail". The answer is remembered; a refusal is never asked again ([Scripting OS X](https://scriptingosx.com/2020/09/avoiding-applescript-security-and-privacy-requests/)) **[R]**. | Not applicable while a person is present. After a refusal: immediate -1743 on every run. |
| Agent CLI running inside a terminal | Still the terminal app, not the agent **[V]** (same local check). | Same as above. | Same as above. |
| Desktop agent host or IDE spawning a shell | The host app's bundle. **[R]** A desktop host's built-in terminal was charged to the host's bundle identifier ([claude-code 78582](https://github.com/anthropics/claude-code/issues/78582)). | The user, but only if the host is allowed to prompt. A hardened-runtime host needs the `com.apple.security.automation.apple-events` entitlement and `NSAppleEventsUsageDescription` ([Apple entitlement doc](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.automation.apple-events), [forum 126345](https://developer.apple.com/forums/thread/126345)) **[V]**. | If the host lacks them: immediate -1743, no dialog, no row in System Settings to switch on; `tccd` logs "Policy disallows prompt for <host>; access to kTCCServiceAppleEvents denied" ([claude-code 78582](https://github.com/anthropics/claude-code/issues/78582)) **[R]**. The user cannot fix this; only the host vendor can. |
| Host that ships an unbundled, versioned helper binary, or disclaims its children | The helper binary itself, identified by resolved path **[R]** (TCC database rows keyed by versioned path in [claude-code 77081](https://github.com/anthropics/claude-code/issues/77081)). | The user, again after every update, with a dialog naming the bare file name or version ([claude-code 77081](https://github.com/anthropics/claude-code/issues/77081), [claude-code 23550](https://github.com/anthropics/claude-code/issues/23550)) **[R]**. | Hang rather than error: one report waited 14 minutes before the connection died ([claude-code 23550](https://github.com/anthropics/claude-code/issues/23550)) **[R]**. |
| ssh session | Probably `sshd-keygen-wrapper`, which is what ssh sessions are charged to for Full Disk Access ([forum 806187](https://developer.apple.com/forums/thread/806187)) **[R for files, I for Apple events]**. | Unknown. An ssh login gets its own non-GUI per-session bootstrap namespace, and GUI services register only in GUI namespaces ([TN2083](https://developer.apple.com/library/archive/technotes/tn2083/_index.html)) **[V]**, so the event may not reach Mail at all. | Unknown: could be -600, -1743, or a dialog on the console screen that the remote user cannot see. Needs a hands-on test. |
| launchd agent in the GUI session (`LimitLoadToSessionType` Aqua, the default) | The job's own program, since there is no parent app. A LaunchAgent shell script calling `osascript` was logged with the script as responsible and `com.apple.osascript` as the accessing process ([Jamf thread](https://community.jamf.com/general-discussions-2/pppc-with-codesigned-script-as-launchagent-18867)) **[R]**. For a job that runs amail directly this would be the amail binary **[I]**. `AssociatedBundleIdentifiers` in the job plist is an input that can attribute the job to an app ([forum 751802](https://developer.apple.com/forums/thread/751802), [forum 678819](https://developer.apple.com/forums/thread/678819)) **[V]**. | The logged-in user, at whatever moment the job fires, with a dialog naming a binary they may not recognise **[I]**. | The call hangs "indefinitely (observed: 2–15+ minutes) rather than failing fast" ([claude-code 84071](https://github.com/anthropics/claude-code/issues/84071)) **[R]**. Historic behaviour in the 10.14 betas was an automatic "no" after two minutes with no re-prompt ([Shirt Pocket](https://www.shirt-pocket.com/blog/index.php/shadedgrey/comments/macos_mojave_opening_new_vistas_in_security_for_mac_users/)), later reported as changed ([Michael Tsai's roundup](https://mjtsai.com/blog/2018/08/31/aedeterminepermissiontoautomatetarget-added-but-aepocalyse-still-looms)) **[R]**. |
| launchd daemon (system context) | Not meaningful: a daemon lives in the global bootstrap namespace and cannot see GUI apps in a user's login session ([TN2083](https://developer.apple.com/library/archive/technotes/tn2083/_index.html)) **[V]**. | Nobody. | Expected immediate failure before TCC is consulted, most likely -600 **[I]**. Not a supported way to run amail. |
| cron | Probably `/usr/sbin/cron`, which is what cron jobs are charged to for file access ([cron on Ventura](https://brandur.org/fragments/modals-mysterious-macos-cron-failures)) **[R for files, I for Apple events]**. | Unknown; cron is started outside the GUI session. | Unknown, same candidates as ssh. For file permissions Apple DTS states prompts "only show up if the process is running in a GUI login session. If not, the operation is allowed or denied based on existing information. If there's no existing information, the operation is denied by default" ([forum 678819](https://developer.apple.com/forums/thread/678819)) **[V for Files and Folders, I for Apple events]**. |

Three distinct "nobody answered" outcomes therefore exist, and they need different handling:

1. **Prompting is forbidden for the responsible client.** Immediate -1743. No dialog will ever appear.
2. **A dialog is on screen and unanswered.** The send blocks. amail's `DefaultTimeout` of two minutes kills `osascript` and prints "Mail did not answer within 2m0s", which is indistinguishable from a slow Mail. Whether the dialog stays on screen after the sender is killed, and whether a late click still records a grant, is untested.
3. **No GUI session exists.** Expected immediate denial or -600 **[I]**.

## Error code reference

Constants are from the macOS SDK headers `AppleEvents.h` and `AEMach.h` **[V]**. Output formats were captured locally by raising the numbers inside a script (`osascript -e 'error number -1743'`), which sends no Apple event **[V]**.

| Number | Constant | Meaning | Text on this Mac (interface language en-IN) |
| --- | --- | --- | --- |
| -1743 | `errAEEventNotPermitted` | "the target of the AppleEvent does not allow this sender to execute this event". Returned after the user refuses, and when policy forbids prompting. | `Not authorised to send Apple events to <app>.` |
| -1744 | `errAEEventWouldRequireUserConsent` | Consent has not been decided and the caller asked not to prompt (`kAEDoNotPromptForUserConsent` send mode, or `askUserIfNeeded` false). Never produced by a plain `osascript` run, which always allows prompting **[I]**. | `An error of type -1744 has occurred.` (no dedicated string) |
| -600 | `procNotFound` | The target is not running or not reachable from this session. | `Application isn’t running.` |
| -1712 | `errAETimeout` | The event got no reply in time. Also the plausible result of an unanswered consent dialog **[I]**. | `AppleEvent timed out.` |
| -1750 | `errOSASystemError` | Reported from in-process `NSAppleScript` in an unsigned CLI "with zero helpful context" ([write-up](https://steipete.me/posts/2025/applescript-cli-macos-complete-guide)) **[R]**. | not captured |

How `osascript` surfaces them **[V]** (`man osascript` plus local capture):

- Script errors go to stderr by default; `-s o` sends them to stdout instead. Exit status is 1 for a script error and 2 for a usage error.
- AppleScript form: `0:18: execution error: Not authorised to send Apple events to current application. (-1743)`. The leading numbers are a source range.
- JavaScript for Automation form: `execution error: Error: Error: <message> (-1743)`, with no source range.
- The number in parentheses is the last token on the line in both forms.

Localisation **[V]**: the message strings come from the AppleScript component's string table, which ships 41 localisations. Samples for -1743: `Not authorized to send Apple events to …` (en), `Not authorised to send Apple events to …` (en_GB, en_AU, and observed on this en-IN Mac), `Keine Berechtigung zum Senden von Apple-Events an …` (de), `Non autorisé à envoyer des évènements Apple à …` (fr), and a Japanese string with no Latin words at all. Another Mail tool shipped a bug where an en_GB system was misdiagnosed as "no accounts" because it matched the American spelling ([apple-mail-mcp 218](https://github.com/sweetrb/apple-mail-mcp/issues/218)) **[R]**. Match the number, never the text.

Notes for `internal/mail/client.go` as it stands:

- It already matches `-1743` and `-1712` by number. Good.
- It searches the whole stderr for the substring, so a subject line or address containing "-1743" inside an unrelated error would be misreported. Anchoring on the trailing `(-1743)` is tighter.
- The hint says "this terminal is not allowed to control Mail". Under a desktop host, a LaunchAgent or a disclaimed binary the holder is not a terminal, and under a host that cannot prompt the advice to enable it in System Settings cannot be followed.
- Whether the `execution error: ` prefix is itself localised was not established; the string is not present as plain text in the `osascript` binary.
- A script that catches the exception and returns JSON must pass on `errorNumber`, not `message`.

## Checking, resetting and pre-granting

**Checking without a prompt.** `AEDeterminePermissionToAutomateTarget(target, typeWildCard, typeWildCard, false)` returns `noErr` (granted), -1743 (denied), -1744 (not decided yet) or -600 (target not running) and shows nothing ([Apple doc](https://developer.apple.com/documentation/coreservices/3025784-aedeterminepermissiontoautomatet), SDK header) **[V]**. Behaviours that matter:

- The target must already be running; otherwise the answer is -600 and says nothing about permission **[V]**.
- It answers for the responsible client, not for the calling binary. Locally, an unsigned interpreter process under a terminal that already holds the grant got `noErr` **[V]**.
- With `askUserIfNeeded` true it blocks until the user answers, and the header says not to call it on the main thread **[V]**.
- Under the hardened runtime without the Apple Events entitlement it returns -1743 even with `askUserIfNeeded` true and never prompts ([forum 130949](https://developer.apple.com/forums/thread/130949)) **[R]**.
- In the 10.14 betas it returned -1744 even after a refusal ([write-up](https://www.felix-schwarz.org/blog/2018/08/new-apple-event-apis-in-macos-mojave)) **[R]**; current behaviour after a refusal was not tested here.
- `kAEDoNotPromptForUserConsent` on `AESend` gives the same fail-fast -1744 for a real event **[V]**. This is the only documented way to turn "hang on an unanswerable dialog" into an immediate error, and it is not reachable through the `osascript` command line.

mailctl uses exactly this probe for its `permissions --check` command ([source at 5ba83d6](https://github.com/zydtiger/mailctl/blob/5ba83d63fca3b78cfc6d42e8658bae411839f296/src/permissions.rs)) **[V, read]**.

**Resetting.** `tccutil reset AppleEvents [bundle_id]` is the only supported command; it removes decisions so the next access prompts again (`man tccutil`) **[V]**. It accepts a bundle identifier only: `tccutil: Usage: tccutil reset SERVICE [BUNDLE_ID]` **[V]**. A client recorded by path cannot be reset on its own; an attempt with a made-up identifier fails with "No such bundle identifier" ([claude-code 23550](https://github.com/anthropics/claude-code/issues/23550)) **[R]**, leaving only the global reset, which wipes every app's Automation decisions. Users can also flip the switch under System Settings, Privacy & Security, Automation, provided a row exists.

**Pre-granting.** A Privacy Preferences Policy Control profile has an `AppleEvents` array whose entries need `Identifier`, `IdentifierType` (`bundleID` or `path`; "Nonbundled binaries must be identified by installation path"), a mandatory `CodeRequirement`, `Authorization` (macOS 11 and later) and, for this service, `AEReceiverIdentifier`, `AEReceiverIdentifierType` and `AEReceiverCodeRequirement` ([Apple's published schema](https://github.com/apple/device-management/blob/release/mdm/profiles/com.apple.TCC.configuration-profile-policy.yaml)) **[V]**. Such profiles only take effect when delivered by an approved MDM, and only Developer ID signed clients can realistically be pre-approved ([Scripting OS X](https://scriptingosx.com/2020/09/avoiding-applescript-security-and-privacy-requests/)) **[R]**. For amail today the entry would have to name the terminal or host app as sender. An ad hoc signed amail has a code requirement that is just its hash (see below), so a profile would need rewriting for every build.

## Options for making the binary its own permission holder

Facts that constrain every option:

- TCC recognises code across versions through its code signature. "If your code is unsigned, or signed ad hoc … the system can't tell that version N+1 of your code is the same as version N, and thus you'll encounter excessive prompts" ([forum 678819](https://developer.apple.com/forums/thread/678819)) **[V]**.
- Go links ad hoc signed binaries on Apple silicon and Homebrew installs them that way. A Homebrew-installed Go CLI on the development Mac shows `Signature=adhoc`, `flags=adhoc,linker-signed`, `Identifier=a.out`, `Info.plist=not bound`, `TeamIdentifier=not set`, and a designated requirement of `cdhash H"…"`, at a resolved path that contains the version number **[V]**. So both the hash and the path change on every `brew upgrade`, and on every `go install` rebuild.
- Unbundled clients are recorded by resolved path **[R]** ([claude-code 77081](https://github.com/anthropics/claude-code/issues/77081)); mailctl's README says the same in its own words: "An ad-hoc signed rebuild is a new binary to macOS: run `mailctl permissions` again" ([README](https://github.com/zydtiger/mailctl/blob/5ba83d63fca3b78cfc6d42e8658bae411839f296/README.md)) **[R]**.
- Responsibility is a property of the process tree, not of who sends the event. Sending Apple events from inside the amail process does not by itself move the grant off the terminal **[I, consistent with the local check above]**.

| Option | What it requires of amail | What the user gets | Cost and risk |
| --- | --- | --- | --- |
| 0. Keep the host as holder (today) | Nothing. | One grant per terminal or host app. Broken with no remedy inside hosts that cannot prompt. | Free. Should at least stop calling the holder "this terminal" and say which contexts are unsupported. |
| 1. Disclaim and re-exec, keep `osascript` | On start, `posix_spawn` a copy of itself with `responsibility_spawnattrs_setdisclaim(&attr, 1)` set, mark the child through an environment variable, wait and forward the exit status and signals. The symbol is private; resolve it at run time and fall back to running in place when absent. It is still exported by libSystem on macOS 26.6 **[V]**. Go needs cgo, or a run-time `dlsym` bridge, to call it. | One grant to "amail" that works from every terminal, IDE and agent host, including hosts that cannot prompt. `osascript` started by the disclaimed process is charged to it ([mailctl source](https://github.com/zydtiger/mailctl/blob/5ba83d63fca3b78cfc6d42e8658bae411839f296/src/responsibility.rs), stated for macOS 26.6) **[R]**. | About a hundred lines. Undocumented call, also used by LLDB, Chromium, Firefox and Qt Creator ([Qt write-up](https://www.qt.io/blog/the-curious-case-of-the-responsible-process)) **[R]**. With ad hoc signing the user is re-prompted after every upgrade and stale rows pile up in System Settings. The dialog names a bare file name. The per-client reset command does not work for a path client. |
| 2. Option 1 plus an embedded Info.plist | Link an `Info.plist` into the `__TEXT,__info_plist` section carrying `CFBundleIdentifier`, `CFBundleName` and `NSAppleEventsUsageDescription`. With cgo this is one directive, `#cgo LDFLAGS: -Wl,-sectcreate,__TEXT,__info_plist,${SRCDIR}/Info.plist`; the flag is on Go's linker-flag allowlist ([security.go](https://github.com/golang/go/blob/master/src/cmd/go/internal/work/security.go)) **[V]**, so it survives `go install` as long as cgo and the command line tools are present. | A usage string in the dialog and a bundle identifier. Apple DTS points at exactly this build setting for bare tools and notes that `sshd-keygen-wrapper` carries such a section ([forum 806187](https://developer.apple.com/forums/thread/806187)) **[V]**. | Makes cgo mandatory, which ends pure Go cross-compilation. Whether TCC then records an ad hoc signed tool by bundle identifier instead of path, and whether that survives an upgrade, is unknown. A hash-only requirement still changes per build, so persistence is unlikely without option 3 **[I]**. |
| 3. Developer ID signature and notarisation | A paid Apple developer membership, signing and notarising release binaries in CI, and distributing those prebuilt binaries (a tap formula or cask that downloads them). With the hardened runtime the binary needs the Apple Events entitlement and the usage string ([forum 126345](https://developer.apple.com/forums/thread/126345)) **[V]**. | A stable identity: grants persist across upgrades, and MDM pre-approval becomes possible. | Annual fee, secrets in CI, a release pipeline. Does nothing for source builds: `go install` and Homebrew source bottles remain ad hoc. On its own it does not move responsibility off the terminal; it has to be combined with option 1 or 5. |
| 4. Send Apple events in-process | Replace the `osascript` child with `OSAKit` or `NSAppleScript` through cgo and Objective-C, running the same JavaScript for Automation sources. Apple DTS prefers this: it "runs the code inside your process, which simplifies the TCC story" ([forum 750802](https://developer.apple.com/forums/thread/750802)) **[V]**. | Real status codes instead of parsed stderr, the silent permission probe, and the do-not-prompt send mode for fail-fast behaviour in unattended runs. | Largest change: cgo, an Objective-C bridge, and a second code path to test. Still needs option 1 to become the holder, and option 3 to keep the grant. |
| 5. Ship inside an app bundle | Put the binary in a minimal `.app` and link it onto the PATH. Apple DTS recommends this shape for tools that need Full Disk Access: "take your command-line tool and stick it inside an app bundle, then use it exactly the way you were using it before" ([forum 806187](https://developer.apple.com/forums/thread/806187)) **[V]**. | A proper name, icon and row in System Settings, and immunity from the macOS 26.1 listing bug below. | Needs cask-style distribution and, realistically, option 3. Whether a bundled tool started from a terminal is charged to its bundle or to the terminal without disclaiming was not established; the Qt write-up says a terminal-launched app is charged to the terminal **[R]**. |

A cheap step that is independent of all of the above: probe before the first real event. The silent query answers for the same responsible client that `osascript` will be charged to, so amail could tell "not decided yet" from "refused" from "Mail is not running" up front and refuse to proceed in an unattended run instead of hanging. Reaching the query needs cgo, a run-time `dlsym` bridge, or possibly the Objective-C bridge inside a JavaScript for Automation script; the last route is untested.

## What changed in macOS 14, 15 and 26

No Apple release note describing a change to Automation prompts in these releases was found. What turned up:

- **Baseline, macOS 10.14.** Consent for Apple events, `AEDeterminePermissionToAutomateTarget`, -1744 and the do-not-prompt send mode all date from here (SDK header availability) **[V]**.
- **macOS 13.** `AssociatedBundleIdentifiers` in launchd job plists, documented in `man launchd.plist` for the Login Items list and named by Apple DTS as an input to responsibility **[V]**.
- **macOS 14.** Nothing specific to Automation found. The fix below was not backported to 14.7.6 according to the researcher who reported it **[R]**.
- **macOS 15.** 15.5 fixed CVE-2025-31250, a flaw in the indirect access request path used for Apple events that let a consent dialog name one app while recording the grant for another; malformed requests are now silently dropped ([researcher's write-up](https://wts.dev/posts/tcc-who/)) **[R]**. No behaviour change for well-formed senders was reported.
- **macOS 26.** In 26.1 and 26.2, plain executables stopped appearing in privacy panes (Full Disk Access, Screen Recording, with Accessibility also reported) even though grants still worked; Apple DTS called it a bug, and it was reported fixed in the 26.3 beta ([forum 806187](https://developer.apple.com/forums/thread/806187), [forum 807898](https://developer.apple.com/forums/thread/807898)) **[V that DTS confirmed the bug, R for the fix]**. Whether the Automation pane was affected is not stated. In the same threads Apple DTS said bare executables have "only ever been 'fully' supported" as bundled code for Full Disk Access, which is a warning for options 1 and 2. On 26.6 the disclaim symbol is still exported **[V]** and mailctl documents its self-attribution as working **[R]**.
- **Across 26.x**, most field reports are about agent hosts rather than the OS: hosts without the entitlement that can never prompt, and hosts whose helper path changes per update so the user is asked again each time (issues linked in the table above) **[R]**.

## Open unknowns that need a hands-on test

Each needs a deliberate prompt or a TCC reset, so none was run. A disposable macOS virtual machine restored from a snapshot before each run is the method Apple DTS suggests.

1. **ssh.** With the same user logged in at the console, and with nobody logged in: which client is charged, does a dialog appear on the console, and what does `osascript` print and how quickly?
2. **cron and LaunchAgent.** Same questions for a crontab entry and for a LaunchAgent that runs amail directly. Does an unanswered dialog end in -1712 after the Apple event timeout, in -1743, or never?
3. **Killed sender.** After amail's deadline kills `osascript`, does the dialog stay up, and does a late "Allow" record a grant that the next run can use?
4. **Disclaimed Go binary.** Does a disclaimed, ad hoc signed Go build get a dialog naming it, does its `osascript` child inherit the grant, and what does the row look like in the Automation pane on 26.6?
5. **Upgrade persistence.** After rebuilding at the same path, and after a Homebrew upgrade to a new versioned path, is the grant kept, re-prompted or silently refused? Does an embedded `Info.plist` with a bundle identifier change the answer, and can `tccutil reset AppleEvents <that identifier>` then reset it?
6. **Usage string with an `osascript` child.** When the disclaimed parent holds the grant but `osascript` sends the event, is the parent's `NSAppleEventsUsageDescription` shown, and is its absence ever fatal?
7. **Probe after refusal.** Does the silent query return -1743 or -1744 once the user has refused, on macOS 26?
8. **Probe from a script.** Can the silent query be called through the Objective-C bridge of a JavaScript for Automation script, avoiding cgo altogether?
9. **Localised prefix.** Is `execution error: ` translated under a non-English interface language? The client currently splits on it.
10. **Desktop hosts in the wild.** Which commonly used agent hosts and IDE terminals can prompt at all today; the reports above cover only one vendor.
